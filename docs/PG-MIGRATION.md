# SQLite → PostgreSQL 全量迁移

> 子命令 `bot-harness migrate` 与校验器。本文只描述**这一步**：把线上 SQLite 的
> 全量数据搬进 PostgreSQL 并证明一次搬运没有丢东西。
>
> 运行时的 PostgreSQL 方言（`internal/store/dialect.go` + `pg.go` 的 `pgSchema`）**已经实现**，
> 两边建出来的表在列/类型/可空/默认/identity/索引/**UNIQUE 约束名**上完全等价（见 §5）。
> 决策与代价记在 [DECISIONS.md](DECISIONS.md) 的 **D-039**（时间列另见 **D-040**）；日常切换步骤见
> [README §1.1](../README.md) 与 [AGENTS.md §1](../AGENTS.md)。
>
> **§8 的实测数据来自一次演练（快照副本 + 临时库），§8.1 是一次生产切换的验收记录。**
>
> 时间列随后又从 `TEXT` 换成原生 `TIMESTAMPTZ`（见 **§12**）。本文里凡是出现
> 「时间仍是 TEXT」的句子，描述的都是**迁移当时**的状态，不是当前实现。

## 1. 用法

```bash
# 计划（绝不写库）
bot-harness migrate --from /data/bot.db --to 'postgres://bot:<口令>@postgres:5432/bot?sslmode=disable' --dry-run

# 正式搬运：建表 → 逐表一个事务 → setval → 立刻自校验
bot-harness migrate --from /data/bot.db --to 'postgres://bot:<口令>@postgres:5432/bot?sslmode=disable'

# 只校验，不写
bot-harness migrate --from /data/bot.db --to 'postgres://bot:<口令>@postgres:5432/bot?sslmode=disable' --verify-only

# 重跑（目标表非空必须显式 --replace；无该标志会被拒绝并列出各表行数）
bot-harness migrate --from /data/bot.db --to 'postgres://bot:<口令>@postgres:5432/bot?sslmode=disable' --replace
```

省略 `--to` 时读**进程自己的** `DATABASE_URL`。在容器里跑（`docker exec bot-harness …`）那正是
`env_file` 注入的那一份，所以 `docker exec … --from /data/bot.db` 就够了；
**不要写成 `--to "$DATABASE_URL"`** —— 双引号会先被**宿主机** shell 展开，通常得到空串或另一个值。

| 参数 | 含义 |
|---|---|
| `--from` | 源 SQLite 路径（**只读打开**，见 §3） |
| `--to` | 目标 DSN；缺省读 `DATABASE_URL` |
| `--dry-run` | 打印建表 DDL、逐表行数、目标现状、序列计划；一个字节都不写。序列计划与实跑**同一公式**（`GREATEST(max(pk), sqlite_sequence)+1`），memories 没有特殊分支 |
| `--verify-only` | 只跑校验，不建表不写数据 |
| `--replace` | 先 `TRUNCATE ... RESTART IDENTITY` 再搬 |
| `--batch` | 非 media 表的每批行数（默认 1000）；media 强制 ≤ 16 |
| `--timeout` | 整体时间预算（默认 30m） |

退出码：0 成功（含校验通过）；1 迁移或校验失败；2 参数错误。

## 2. 表顺序

```
schema_migrations → settings → conversations → dedup → stats → proactive_state
→ messages → records → tool_calls → scheduled_tasks → commitments → human_status
→ affect_states → affect_events → affect_history → join_decisions → join_topics
→ memories → media
```

原有的十一张表顺序**原样保留**，新表 `commitments` / `human_status` / `affect_*` /
`join_*` 插在 `scheduled_tasks` 与 `memories` 之间，`media` 仍然最后。
`schema_migrations` 排在最前，因为它记录源库已应用的迁移。
media 压尾是刻意的：44 MiB 的 BLOB 是唯一昂贵的表，失败时不该让便宜的表先搬完再卡在它上面。

**旧 SQLite 文件兼容**：新表是升级后才存在的，`source.discover()` 把这些表视为
`optionalTables` —— 源库里没有就跳过（目标库由运行时 `pgSchema` 在下次启动时补建），
不会因为「源库还没有新表」拒绝整次迁移。源库已有这些表时照常搬运 + 校验。

## 3. 安全性

- **源只读**：`sql.Open("sqlite", "file:"+path+"?mode=ro")`，且 `SetMaxOpenConns(1)`。
  迁移器物理上无法改生产库；`TestSourceOpenIsReadOnly` 钉住这一点。
- **每表一个事务**：中途失败该表整体回滚，目标停留在「上一张表已完成」的状态，
  配合 `--replace` 重跑永远安全。
- **目标非空默认拒绝**：不是静默覆盖，而是列出每张非空表的行数并退出 1。
- **不碰业务进程**：子命令是独立进程，不加载 dispatcher / QQ / admin，
  只开关两个数据库连接。

## 4. 动态列发现（不硬编码列）

- 源：`PRAGMA table_info(<t>)` → 列名、声明类型、NOT NULL、默认值、主键序号；
  `PRAGMA index_list/index_xinfo` → 二级索引与 UNIQUE 约束；
  `sqlite_master` → 是否 AUTOINCREMENT；`sqlite_sequence` → 自增计数器。
- 目标：`information_schema.columns`（`current_schema()`）缓存表→列→类型。
- 搬运的列清单 = 源发现顺序，直接用于 `SELECT` 与 `COPY`。
- 目标已存在但**缺列**时硬失败（拒绝往更窄的表里搬）；目标多出的列必须是可空或有默认值。

## 5. 目标 schema

按运行时 store 的 `internal/store/pg.go`（`pgSchema`）对齐，并逐项比对过
（`information_schema.columns` / `pg_indexes` / `pg_constraint` 全量 diff）：
**列集合、类型、可空性、默认值、identity 标记、索引定义、约束定义全部一致** ——
`memories` 的 UNIQUE 约束名也已对齐（见本条末尾）。

- 非时间列的类型只用 `TEXT` / `INTEGER` / `BIGINT` / `DOUBLE PRECISION` / `BYTEA`；
  时间列是 **`TIMESTAMPTZ`**（18 列：13 列 `NOT NULL`，5 列可空）。迁移器（`internal/pgmigrate/ddl.go`
  的 `timestampColumns` / `nullableTimestampColumns`）与运行时 store（`internal/store/pg.go` 的
  `pgSchema`）各自持有一份列清单，**两份必须一致**（这是 D-039「代价 3：双方言维护」的一部分，没有变轻）；
  两条路建出来的库在时间列上等价这件事，由 `TestTargetTimestampColumnsAreTimestamptz` 钉住。
- `INTEGER PRIMARY KEY AUTOINCREMENT` → `BIGINT GENERATED BY DEFAULT AS IDENTITY`
  （显式 id 可插，序列可 setval）。
- 布尔仍是 `INTEGER`（`enabled` / `addressed`），Go 侧按 int 读、与 1 比较，行为不变。
- **时间列是原生 `TIMESTAMPTZ`**（2026-11-02 由 `TEXT` 改来，见 §12）：
  13 个非空列 `TIMESTAMPTZ NOT NULL`；5 个「空串表示未设置」的列
  （`proactive_state.last_sent_at`、`proactive_state.updated_at`、`scheduled_tasks.lease_until`、
  `scheduled_tasks.sent_at`、`memories.last_used_at`）改成**可空、无默认值**的 `TIMESTAMPTZ`
  （`NULL` = 未设置）。**Go 侧仍以 RFC3339 字符串交互**：写的是字符串参数，读回来是
  `2026-11-02T02:31:05+08:00` 形式的字符串，API 输出与迁移前逐字节一致 —— 时区语义只在
  数据库里，不在 Go 的字符串里。
- **不建任何外键**：`records` 里有 111 行 `conversation_id` 孤儿，必须原样保留。
- 列默认值从源抄过来（`DEFAULT ''` / `DEFAULT 0` / `DEFAULT 1` / `DEFAULT 'dialogue'`），
  这样运行时省略列的 INSERT 在切换后仍然可用。表达式类默认值（`CURRENT_TIMESTAMP`）
  会被丢弃并可在 `--dry-run` 看到——本库没有这种列。
- UNIQUE 约束按 PostgreSQL 自己的命名规则重建
  （`memories_scope_group_openid_member_openid_text_key`）。
  **store 侧已对齐**：`internal/store/pg.go` 的 `pgSchema` 也写这个名字
  （`memoriesUnique` 常量），不再是早期的 `uq_memories_scope_group_openid_member_openid_text`。
  两个来源建出的库在**列/类型/可空/默认/identity/索引定义/约束名**上全部等价。

  历史库升级：改名之前 store 建过的库仍带着旧名，所以每次打开 PG 都会跑一次
  `normalizeMemoriesUnique`（幂等）：

  | 目标库现状 | 动作 |
  |---|---|
  | 只有旧名 | `ALTER TABLE memories RENAME CONSTRAINT uq_… TO …_key`（不丢数据、不阻塞写入） |
  | 两个名字都在、且 `conkey` 相同 | `DROP CONSTRAINT uq_…`（清掉多出来的冗余唯一索引） |
  | 两个名字都在、但 `conkey` 不同 | 不动（不是本条约束，误删会真的丢约束） |
  | 只有新名 | 无操作 |

  回滚就是把该函数里的 `legacyMemoriesUnique` / `memoriesUnique` 对调后执行一次
  （反向 `RENAME CONSTRAINT`），同样幂等。回归测试：
  `internal/store/pg_normalize_test.go`（三种状态）与
  `internal/store/pg_migrate_interop_test.go`（store 建库后跑 `pgmigrate.EnsureSchema`，
  必须仍然只有一条唯一约束）。
- `media.size` 用 `BIGINT`（与 store 的写法一致），其余整数列 `INTEGER`。
  这条是唯一的按列覆盖，写在 `columnTypeOverrides` 里，不影响动态列发现。
- **join_gate v2 的两处增量**（`join_decisions.action` 与 `messages(quote_index)` 索引）：

  | 对象 | 类型 / 定义 | 说明 |
  |---|---|---|
  | `join_decisions.action` | `TEXT NOT NULL DEFAULT ''` | 三分类 `join` / `wait` / `skip`；**有默认值**，所以老版本 INSERT 省略该列仍然可用（代价是把 `action` 读成 `''`，UI 按 `joined` 回退） |
  | `idx_messages_quote_index` | `CREATE INDEX IF NOT EXISTS … ON messages(quote_index)` | 引用机器人识别要按 `group_openid + quote_index` 反查 assistant 消息；v2 之前 SQLite 只在 base schema 里建了列、PG 连索引都没有 |

  - `action` 在 `pgSchema` 的 `CREATE TABLE IF NOT EXISTS join_decisions` 里直接建；
    `quote_index` 的列本身来自迁移 `0008_messages_quote_index`（PG 侧已 baseline，列在
    `pgSchema` 的 `messages` 定义里），**v2 新增的只是索引**。
  - 迁移器（`internal/pgmigrate`）**按源库实际列与索引动态发现**，所以 SQLite 老库没有
    `action`、或没有该索引时，它照样能搬：列清单取自源库 `PRAGMA`，索引取自
    `index_list/index_xinfo`。若源库是 v2 之后建的，目标库会一并得到列与索引。
  - **索引自动补**：`pgSchema` 每次打开库都会执行（`CREATE TABLE IF NOT EXISTS` +
    `CREATE INDEX IF NOT EXISTS`），所以已有的 PG 库在下次启动时就会得到
    `idx_messages_quote_index`，**不需要手工建索引**。
  - **列不会自动补**：`CREATE TABLE IF NOT EXISTS` 不会给已存在的表加列，PG 的
    `0014_join_gate` 又是 baseline（不执行 `ALTER`，见 `baselineMigrations`）。
    因此一个**用 v1 构建建过 `join_decisions` 的 PG 库**（0.3.0 尚未发布，只有在本分支
    的早期构建上跑过才会遇到），升级到 v2 代码后缺少 `action` 列，需要一次性执行：

    ```sql
    ALTER TABLE join_decisions ADD COLUMN IF NOT EXISTS action TEXT NOT NULL DEFAULT '';
    ```

    什么时候必须做：`migrate` 的 `EnsureSchema` 对**已存在的目标表**只补二级对象、
    不补列，并且源表有而目标缺列时会**硬失败**（`refusing to migrate into a narrower
    schema`，见 `internal/pgmigrate/target.go`）。所以「v2 的 SQLite → v1 建过的 PG」
    这条路径必须先跑上面的 `ALTER`，否则整次搬运会被拒绝。
    不需要做的：全新建的 PG 库（`pgSchema` 直接带 `action`）与由 v2 源库经 `migrate`
    建出来的库（建表 DDL 取自源库列清单）。
    > 这是 v2 的**已知待办**：SQLite 侧 `migrationJoinGate` 已经用 `tableColumns` 做
    > 幂等补列，PG 侧目前没有等价逻辑；在 `migratePostgres` 里补上之后，本段手工 SQL 应删掉。

**源表已存在时**：只补齐缺失的二级对象（`CREATE INDEX IF NOT EXISTS`，
UNIQUE 约束先查 `pg_constraint`，**按本工具自己算出的名字**查），不重建表、不改列——
store 建的表原样复用，UNIQUE 约束按同一个名字查 `pg_constraint`，不会重复添加。

## 6. 序列

五个 IDENTITY 表（messages / records / tool_calls / scheduled_tasks / memories）统一一条语句：

```sql
SELECT setval(pg_get_serial_sequence('<t>', '<pk>'),
              GREATEST(COALESCE((SELECT MAX("<pk>") FROM "<t>"), 0), <seq>), true)
```

其中 `<seq>` 是源 `sqlite_sequence.seq`。`--dry-run` 打印的计划用同一式子（代码里是
`nextIDFromState(maxID, seq)`，实跑、计划、校验器三处共用），所以计划里的数字就是
实跑会写下的数字。这条式子对三种形态都成立：

| 形态 | max(pk) | seq | setval | 下一个 id |
|---|---|---|---|---|
| messages（1448 行，max id 13343） | 13343 | 13343 | 13343 | **13344** |
| memories（0 行，但计数器已用过 1 次） | 0 | 1 | 1 | **2** ✅ |
| 从未写入过的表 | 0 | 无 | 0 | 1 |

`GREATEST` 同时兜住「计数器过期」：如果曾有显式 id 超出计数器，max(pk) 胜出，
序列不会重发已占用的 id。**memories 不需要特殊分支**——早期版本写死 setval(1)，
一旦 memories 真有行就会退回到重发 id 2 的错误状态，已由 `TestRoundTripAgainstPostgres`
（fixture 里给 memories 塞 3 行）钉住；`--dry-run` 的同类硬编码（写死 `memories.id=2`）
也已删除，由 `TestDryRunSequencePlanMatchesTheRun`（3 行 + 计数器 4 → 计划打印 5）钉住。

## 7. 校验器（--verify-only）

逐表三件事：

1. **行数**：源 `COUNT(*)` vs 目标 `COUNT(*)`。
2. **全列规范化有序 sha256**：两侧都按主键 `ORDER BY` 流式扫描，每行编码后取 sha256，
   再把这些 32 字节摘要依次喂进聚合 sha256。两侧聚合哈希相等 ⇔ 行集合与顺序完全一致。
3. **逐表附加证据**：
   - `media`：每行 `sha256(data)` 必须同时等于 `id` 与 `sha256` 列，
     并且两侧「每行摘要串联后的 sha256」一致（per-row sha256 + 聚合哈希）。
   - `settings`：逐键做 **JSON 语义等值**比较（键序、`1` vs `1.0` 视为相等），
     并报告只在单侧存在的键。
   - 五个 IDENTITY 表：`last_value`/`is_called` 推出的下一个 id 必须等于
     `max(pk)+1`（空表时按计数器算，memories 即 2）。

**行编码** `len:tag:value`，长度是 payload 的**字节数**：

| tag | 含义 | payload |
|---|---|---|
| `N` | NULL | 空 |
| `I` | 整数 | 十进制（int64/int32/int 归一，SQLite INTEGER 与 PG bigint 同码） |
| `F` | 浮点 | 大端 IEEE-754 位模式 8 字节；**整值浮点先降级为 I**，NaN/±Inf 有固定位模式 |
| `S` | 文本 | 原始 UTF-8 字节 |
| `X` | 二进制 | 原始字节 |

行内列之间用 `0x1f` 分隔。不接受未知类型（宁可报错，也不用 `fmt.Sprintf` 兜底，
否则真正的差异会被字符串化抹平）。因为 `len` 是字节长度、`X`/\`S\` 前缀不同，
BLOB `"ABC"` 与 TEXT `"ABC"` 不会碰撞。

**不一致时打印首条差异**：定位到第一个摘要不同的行，按主键回查两侧整行，
逐列比较规范化编码，报出第一个不同的列。实测输出：

```
messages   1448  1448  5137fb29f5aa5e3c 672df19329636c44 MISMATCH
  first difference: row #1 id=11896: column content: expected "绷" got "绷X"
```

## 8.1 一次生产切换的验收记录

停写窗口约 4 分钟：`docker compose stop bot-harness` → 复制 `bot.db`（优雅停机已完成 WAL checkpoint，
卷里只剩主库）→ `migrate` → `--verify-only` → 改 `.env` 的 `DATABASE_URL` → 重建镜像启动。

| 项 | 结果 |
|---|---|
| `migrate` exit code | 0（1.18 s，15,901 行） |
| `--verify-only` | `verification PASSED: 12/12 tables match` |
| 逐表行数 | schema_migrations 10 / settings 31 / conversations 6 / dedup 671 / stats 1054 / proactive_state 0 / messages 1447 / records 12488 / tool_calls 41 / scheduled_tasks 9 / memories 0 / media 144 |
| 序列 | `messages=13344 records=12489 tool_calls=42 scheduled_tasks=10 memories=2` |
| 独立复核 | 用 Python 读 SQLite + psql 读 PG、各自算行哈希后比对（**不复用**本工具的 canonical 编码）：**12/12 相等** |
| 断言 | 外键 0 个、主键 12 个、`media` 144 行 `sha256(data)==id` 违例 0、`sum(size)=44,378,876`、布尔域一致；时间列当时仍是 `TEXT`，25 字符 `+08:00`（`timestamptz` 改写见 §12） |
| 切换后 | `driver=postgres`、`path=""`、`size_bytes`≈64 MB、`readonly.storage` 口令为 `redacted`；人工后台消息与真实群消息均落库（messages 1447→1449、records→12490、media→145） |
| 回滚 | **未触发**；回滚镜像与 SQLite 卷均保留 |

**与任务书参数的一处差异**：源库实际 `messages=1447` / `records=12488`（不是 1448 / 12487），
以源为准判定 PASS。**窗口内（约 4 分钟）到达的群消息不在新库**，这是全量搬运的固有代价。

## 9. 与运行时 store 的合并点

1. **建表来源二选一，结果完全等价**。运行时的 `internal/store/pg.go`（`pgSchema`）若已在目标库跑过，
   迁移器跳过建表、只补索引与 UNIQUE；若没跑过，迁移器自己建。
   列的集合/类型/可空性/默认值/identity 标记/索引定义**等价**（`--dry-run` 会把 DDL 打出来逐条比对），
   `memories` 的 UNIQUE 约束名也已统一（详见 §5）；`internal/store/pg_migrate_interop_test.go`
   钉的就是"store 建库 → 迁移器再跑 → 唯一约束仍然只有一条"。
2. **`migrate` 不依赖 `internal/store`**。它自己带 DDL（`internal/pgmigrate/ddl.go`），
   所以 store 侧改 schema 时它照样能编译、能跑。store 的 schema 变化后，
   只需同步 `columnTypeOverrides` 与 `renderDDL` 的两处约定。
3. **不碰业务代码**：`cmd/bot-harness/main.go` 只加了一个 `case "migrate"` 分支，
   其余零改动；`migrate` 是独立进程，不加载 dispatcher / QQ / admin。

## 12. 时间列迁移（TEXT→timestamptz）

> 时间：2026-11-02（与 §8.1 的 SQLite→PG 切换同一天，**是第二次独立迁移**）。
> 这一步**不动搬运行**，只把已经在 PG 里的 18 个 `TEXT` 时间列换成原生 `TIMESTAMPTZ`。
> 为什么做、代价与未做项见 [DECISIONS.md](DECISIONS.md) 的 **D-040**。

### 12.1 目标形态

| | 迁移前 | 迁移后 |
|---|---|---|
| 类型 | `TEXT`，25 字符 RFC3339（`2026-11-02T02:31:05+08:00`） | **`TIMESTAMPTZ`**（原生带时区时刻） |
| 13 个非空列 | `TEXT NOT NULL` | `TIMESTAMPTZ NOT NULL` |
| 5 个可空列 | `TEXT NOT NULL DEFAULT ''`（`''` 表示未设置） | **可空 `TIMESTAMPTZ`，无默认值**（`NULL` 表示未设置） |
| Go 侧读写 | `string` | **仍是 `string`**，格式仍是 `2026-11-02T02:31:05+08:00` |
| 排序 | 字符串排序（同格式下恰好正确） | 时刻排序（跨时区也正确） |

5 个可空列：`proactive_state.last_sent_at`、`proactive_state.updated_at`、
`scheduled_tasks.lease_until`、`scheduled_tasks.sent_at`、`memories.last_used_at`。
它们迁移前的真实 DDL 是 `NOT NULL DEFAULT ''`（`''` 只是「未设置」的方言），所以迁移必须
**先 `DROP NOT NULL` + `DROP DEFAULT`，再 `ALTER TYPE`**，否则 `NULLIF(c,'')::timestamptz`
产出的 `NULL` 会被旧约束挡下（详见 §12.5 的坑 1、2）。

### 12.2 两个脚本

| 文件 | 作用 |
|---|---|
| `scripts/pg-timestamptz.sql` | 迁移：单事务（`BEGIN … COMMIT`）、幂等（已是的列 `NOTICE` 跳过）、`lock_timeout=15s`（拿不到锁整笔回滚，不排队）、`SET LOCAL TimeZone='Asia/Shanghai'`、结束前 `ANALYZE` 12 张表 |
| `scripts/pg-timestamptz-verify.sql` | 校验：**99 项**（`type` 18 / `nullability` 18 / `default` 5 / `rowcount` 12 / `instant` 18 / `text` 18 / `nullcount` 5 / `nullmap` 5）；任何一行 `bad>0` 就 `RAISE EXCEPTION`，psql 退出码非 0，可直接当门禁 |

**必须与迁移脚本同一个 psql 会话**：

```bash
docker cp scripts/pg-timestamptz.sql        bot-harness-postgres:/tmp/
docker cp scripts/pg-timestamptz-verify.sql bot-harness-postgres:/tmp/
docker exec -it bot-harness-postgres psql -U bot -d bot \
  -f /tmp/pg-timestamptz.sql -f /tmp/pg-timestamptz-verify.sql
```

原因：校验要拿「迁移前的原文」和「迁移后的时刻」逐行对照，而迁移后原文已经读不出来。
迁移脚本因此在**同一会话内**把原文快照进 `TEMP snap_<表>(pk, old_<列>)`；会话一断快照消失，
校验就只剩类型/可空性这类结构检查（脚本会明确标注 SKIP 与 WARNING，不静默放过）。
所以**不要**拆成两条 `docker exec`，**不要**加 `--single-transaction`（脚本自带事务），
**不要**在外面再包一层事务。

### 12.3 执行顺序（停机切换，2026-11-02 实跑）

```bash
# 0) 回滚点先留好：旧镜像打 tag；整库 dump 二选一
docker tag bot-harness:latest bot-harness:pre-timestamptz-<日期>
bash scripts/backup-pg.sh --keep 14                 # 快照目录（带 SHA256SUMS/MANIFEST，restore-pg.sh 直接吃）
# 或（本次实际留下的就是这种：停服后抓的裸 dump）
# docker exec bot-harness-postgres pg_dump -U bot -Fc bot > bot-<UTC 时间戳>.dump

# 1) 停服（旧二进制仍按文本写 timestamptz 列会失败，所以必须在停服窗口内做）
docker compose stop bot-harness

# 2) 停服期间再抓一份冷备（这一步是真正的回滚依托）
docker exec bot-harness-postgres pg_dump -U bot -Fc bot > bot-<UTC 时间戳>.dump

# 3) 迁移 + 校验（★ 同一条命令、同一个会话 ★）

  -f /tmp/pg-timestamptz.sql -f /tmp/pg-timestamptz-verify.sql

# 4) 重建镜像并启动（新二进制才认识 timestamptz）

```

顺序不能换，硬约束只有**一个方向**：**旧代码 + 新 schema 写不进去** —— 旧二进制对可空时间列
仍然绑 `''`，而 `''::timestamptz` 直接报错；而不是可空的列按 text 绑定也会被 PG 要求显式转换。
所以「停服 → 迁移 → 起新镜像」必须一条线，中间不能有旧进程跑着。

反方向（新代码 + 旧 schema）不是硬失败：`nullableTimeText` 对 string 有回退分支、
`pgmigrate` 的投影也按目标列真实类型条件化，旧库仍然能读能校验。**但这只是兼容，不是支持** ——
线上只跑「新 schema + 新代码」这一种组合，不要拿它当灰度手段。

停机时间 = 停服 → 迁移（秒级）→ 校验（秒级）→ 起服务，实测见 §12.4。

### 12.5 已知坑（都已在脚本里处理）

1. **那 5 个「可空」列其实是 `NOT NULL DEFAULT ''`**。只做 `DROP DEFAULT` + `NULLIF` 会报
   `column "lease_until" … contains null values` 并整笔回滚。必须先 `DROP NOT NULL`。
2. **`DROP DEFAULT` 必须在 `ALTER TYPE` 之前**。否则 PG 会尝试把旧默认值 `''` 转成新类型，报
   `default for column ... cannot be cast automatically`。
3. **`to_char(col AT TIME ZONE 'Asia/Shanghai', …OF)` 的偏移是假的**：`AT TIME ZONE` 返回的是
   `timestamp without time zone`，而 `OF` 只对 `timestamptz` 有意义 —— 对无时区 timestamp 它打印
   `+00`（实测 `19:05+08` 渲染成 `2026-11-01T19:05:00+00`），永远不等于原文 `+08:00`。
   两种正确写法：
   - `to_char(col AT TIME ZONE 'Asia/Shanghai','YYYY-MM-DD"T"HH24:MI:SS') || '+08:00'`
     （**不带 `OF`**，自己补后缀；`pgmigrate` 的校验器用的就是这条）；
   - 或者先 `SET TimeZone='Asia/Shanghai'`，再 `to_char(col, '…OF')`（**不写 `AT TIME ZONE`**），
     得到 `+08`（`OF` 只打 2 位小时，所以比对原文时要先把 `+08:00` 归一成 `+08`；
     `pg-timestamptz-verify.sql` 用的就是这条）。
4. **只读事务里不能 `CREATE/DROP TABLE`**（连 TEMP 表也不行）：校验脚本把结果表与期望清单的
   建表放在 `BEGIN … READ ONLY` **之前**。
5. **会话被掐断 = 校验降级**：快照是 `TEMP` 表，断开后 `instant` / `text` / `nullmap` 只能标 SKIP。
   一定要用一条 `psql -f A -f B` 跑完。
6. **`ALTER TYPE` 是全表重写**：持 `ACCESS EXCLUSIVE` 锁、重建该表全部索引（含主键）。
   实测最大单表是 `media`（0.73 s，44 MB TOAST 一并重写），`records` 0.10 s，其余 < 10 ms。
   **没有 Online 路径**，必须在停服窗口里做。
7. **原文时区不统一会误报**：`text` 项要求新值渲染回去与原文逐字相等。若历史数据里混有 `Z` 或
   小数秒，`text` 会 FAIL 而 `instant`（`extract(epoch …)`）仍 OK —— **时刻正确性以 `instant` 为准**，
   `text` 只是「原文格式是否统一」的提示。线上 18 列 100% 是 `+08:00`，为 0 例。

### 12.6 双方言 helper（`internal/store/dialect.go`）

迁移之后两种后端对时间列的表示不同，差异被收在三个函数里，**SQL 仍然只有一份**：

| helper | PostgreSQL | SQLite |
|---|---|---|
| `NullableTimeArg()` | `NULLIF(?, '')::timestamptz`（空串 → `NULL`） | `?`（原样存 `''`） |
| `TimeIsUnset(col)` | `col IS NULL` | `col = ''` |
| `EmptyTimeLiteral()` | `NULL` | `''` |

读侧不依赖任何 SQL 投影：可空列直接 `SELECT` 原生列，由 `nullableTimeText`（`store.go`）扫描 ——
原生时间按 `scanLocation`（`FixedZone("CST", +8h)`）格式化成 RFC3339，`NULL` 变成 `""`；
SQLite 的字符串原样返回。**两个引擎给调用方的都是「`2026-11-02T02:31:05+08:00` 或 `""`」**。

读取端的时区由 **pgx codec** 决定，不在 SQL 里：`openPostgres` 用
`stdlib.OptionAfterConnect(overrideTimestamptzScanLocation)` 给每条连接注册
`TimestamptzCodec{ScanLocation: FixedZone("CST", +8h)}`。不这么做的话 pgx 默认把 `timestamptz` 解成
UTC，`database/sql` 再 `RFC3339Nano` 出来就是 `…Z`，API 输出会整体偏移 —— 这正是"Go 侧仍拿到
`+08:00` 字符串"的实现方式。**换 DSN 时不要试图用 `timezone=` 参数代替它**（对 pgx 的 codec 无效）。
